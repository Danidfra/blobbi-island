# Publishing the official Arcade Ticket definition (kind:31632)

Operational runbook for the human who controls the official Blobbi item issuer.

**This repository contains no signing code and no key material for this event.**
The client only *reads* kind:31632; publishing is deliberately an out-of-band,
human action. Nothing here should be automated into the app.

## 2. The exact event to sign

Generated by `buildGameItemDefinitionEvent` from `@nostr-games/inventory@0.1.0`
using the canonical registry values. Tag order is the builder's. A test
(`src/protocol/arcade-ticket-publication.test.ts`) re-runs the builder and fails
if this file and the builder ever disagree, so what follows is not a hand copy.

**Unsigned event** — save as `arcade-ticket.json`:

```json
{
  "kind": 31632,
  "tags": [
    ["d", "blobbi:currency:arcade-ticket"],
    ["name", "Arcade Ticket"],
    ["type", "currency"],
    ["category", "currency"],
    ["image", "https://assets.blobbi.pet/items/arcade/arcade-ticket-v1.webp"],
    ["version", "1"],
    ["context", "game:blobbi"],
    ["t", "currency"],
    ["t", "arcade"],
    ["alt", "Game item definition: Arcade Ticket"]
  ],
  "content": "{\"effects\":{\"game:blobbi\":{}},\"metadata\":{\"itemId\":\"cur_arcade_ticket\",\"action\":null,\"stages\":[\"egg\",\"baby\",\"adult\"],\"emoji\":\"🎟️\",\"stackable\":true,\"description\":\"Earned by playing games at the Blobbi Island Arcade. Exchange it for exclusive prizes.\"}}"
}
```

### Tag order is the builder's

`dist/index.js:305–340` fixes it: `d`, `name`, `type`, then the optional
`category`, `image`, `model_3d`, `audio`, `symbol`, `rarity`, `max_stack`,
`version`, then `context` tags, then `t` topics, then `a` derivations, then
`alt`, then extras. Hence `version` before `context`, and `alt` last. The builder
coerces `version: 1` to the **string** `"1"`, which is what the tag model
requires.

`content` unescaped, for review:

```json
{
  "effects": { "game:blobbi": {} },
  "metadata": {
    "itemId": "cur_arcade_ticket",
    "action": null,
    "stages": ["egg", "baby", "adult"],
    "emoji": "🎟️",
    "stackable": true,
    "description": "Earned by playing games at the Blobbi Island Arcade. Exchange it for exclusive prizes."
  }
}
```

### Supplied only at signing time

The builder returns exactly three keys — `kind`, `tags`, `content`. Every tag
above is one we passed: it auto-generates nothing, adds no `alt` unless asked,
and emits no `max_stack` and no `created_at`.

| Field | Set by |
| --- | --- |
| `created_at` | the signer, at signing time (unix seconds) |
| `pubkey` | the signer — must be the official issuer |
| `id` | derived from the serialized event at signing time |
| `sig` | the signer |

### Why each field is what it is

| Field | Reason |
| --- | --- |
| `type: "currency"` | The `type` tag is a free string in the package; `currency` distinguishes it from the 19 `consumable` items. |
| `category: "currency"` | Read by `resolveFromDefinition`. Accepted because `currency` is in the adapter's `VALID_CATEGORIES`, which derives from `ITEM_CATEGORIES`. Without it a valid definition would silently resolve to `unknown`. |
| `image` | Production artwork. Preferred over the emoji by the client's visual resolution order. The 19 published definitions have no `image` tag — none has artwork yet — so this is an addition, not a divergence. |
| `version: "1"` | Carried by all 19 published definitions. The definition schema revision, not the item's. |
| `context: "game:blobbi"` | Carried by all 19. Scopes the item to this game and is relay-indexable. |
| `alt: "Game item definition: Arcade Ticket"` | Matches the `Game item definition: <name>` form used by all 19, rather than repeating the description. The human-readable description still travels in `metadata.description`. |
| `metadata.action: null` | The single field that keeps tickets out of every care flow: `useUseItem` throws `Item has no usable action` for a null action. Omitting the key is equivalent — the adapter accepts only a *string* action — but `null` is explicit for a human reading the event. |
| `metadata.stages` | Schema-required by the resolved view model; carries no meaning while `action` is null. |
| `effects: {"game:blobbi": {}}` | Deliberately empty: a currency has no Blobbi stat effects. Keeps the content shape identical to the other 19. |
| `metadata.stackable: true` | Spelled with the `k`, matching all 19 published definitions (19/19 on both relays use `"stackable"`; none uses `"stacable"`). Declarative only: quantities live in the kind:31633 `a` tags as decimal integers, so items stack regardless of this field. Nothing in the package or in Island reads it. |
| `metadata.description` | The only field here that the 19 published definitions do NOT carry (0/19). Kept because `alt` now follows the generic `Game item definition: …` convention, so this is the event's only human-readable copy. Additive and ignored by every existing reader. |
| `t` tags | Single-letter, relay-indexed, so the ticket is discoverable by topic. |
| **no `max_stack`** | No cap intended. The package's quantity helpers already guard `Number.MAX_SAFE_INTEGER`. |
| **no transferability tag** | Transfer is not supported by the Island UI and no such tag exists in the package schema. Product intent is not expressed by inventing tags. |
| **not in the coin shop** | `src/inventory/shop-catalog.ts` prices only consumables and *rejects* a currency price at module load. `priceForAddress` returns `null`, so `usePurchaseItem` refuses it. |

## 4. Signing and publishing

There is **no existing publish script in this repository**, and that is
intentional: no issuer key, no bunker config, no npm task signs official
definitions. `grep` for `31632` finds only documentation and read-side code. The
19 existing definitions were published out-of-band by whoever holds the issuer
key, and this one must be too.

`nak` is already installed on this machine (`~/go/bin/nak`), so the safest path
needs no new tooling and no new script.

### Key-handling rules

- **Never** put the key in a command argument — argv is visible to `ps` and
  lands in shell history.
- **Never** put it in a file in the repo, in `.env`, in an example, or in a
  commit.
- Prefer, in order: **NIP-46 bunker** (the key never reaches this machine) →
  **interactive prompt** (never touches history or argv) → **`ncryptsec`**
  (encrypted at rest, passphrase prompted).

### Recommended: interactive prompt (no history, no argv)

```bash
# 1. Save the unsigned event from §2 (contains no secret).
$EDITOR arcade-ticket.json

# 2. Sign + publish to BOTH relays. --prompt-sec asks for the nsec on a TTY,
#    so it never enters argv, history or the environment.
cat arcade-ticket.json | nak event --prompt-sec --force-sign \
  wss://relay.ditto.pub wss://relay.dreamith.to
```

`nak` prints the signed event (with `id`, `pubkey`, `created_at`, `sig`) and one
success/failure line per relay. **Both must report success.**

Before moving on, check the printed event against §2: the eight tags in the same
order, the same `content`, and `"pubkey": "9efb8d30…63a9"`.

### Alternative: NIP-46 bunker (key never leaves the signer)

```bash
cat arcade-ticket.json | nak event --sec "$BUNKER_URI" --force-sign \
  wss://relay.ditto.pub wss://relay.dreamith.to
```

Set `BUNKER_URI` without leaking it into history — either with a leading space
(needs `HISTCONTROL=ignorespace` / `setopt HIST_IGNORE_SPACE`) or by reading it
from the macOS Keychain in a subshell:

```bash
BUNKER_URI="$(security find-generic-password -s blobbi-issuer-bunker -w)" \
  nak event --sec "$BUNKER_URI" --force-sign wss://relay.ditto.pub wss://relay.dreamith.to \
  < arcade-ticket.json
```

The value is only ever in the process environment for one command, never in a
file and never in history.

### Afterwards

```bash
rm arcade-ticket.json          # it is scratch, not a repository artifact
```

## 5. Verification procedure

Fetch the exact address back from **each relay separately** — a single query
across both cannot tell you which one has it. `nak req` verifies signatures by
default.

```bash
for RELAY in wss://relay.ditto.pub wss://relay.dreamith.to; do
  echo "── $RELAY"
  nak req -k 31632 \
    -a 9efb8d3045ba753f3664d503308b49783356b26a6d5f4b944bfac4239afe63a9 \
    -d blobbi:currency:arcade-ticket "$RELAY"
done
```

Each relay must return exactly one event, and for each one confirm:

| Check | Expected |
| --- | --- |
| signature | accepted by `nak` (it verifies unless `--no-verify`) |
| `kind` | `31632` |
| `pubkey` (issuer) | `9efb8d3045ba753f3664d503308b49783356b26a6d5f4b944bfac4239afe63a9` |
| `d` tag | `blobbi:currency:arcade-ticket` |
| `image` tag | `https://assets.blobbi.pet/items/arcade/arcade-ticket-v1.webp` |
| `content` | byte-identical to §2 |
| canonical address | `31632:9efb8d3045ba753f3664d503308b49783356b26a6d5f4b944bfac4239afe63a9:blobbi:currency:arcade-ticket` |

A one-line pass/fail for the fields that are easy to misread:

```bash
nak req -k 31632 \
  -a 9efb8d3045ba753f3664d503308b49783356b26a6d5f4b944bfac4239afe63a9 \
  -d blobbi:currency:arcade-ticket wss://relay.ditto.pub \
| jq -e '
    .kind == 31632
    and (.tags | map(select(.[0]=="d"))[0][1]) == "blobbi:currency:arcade-ticket"
    and (.tags | map(select(.[0]=="image"))[0][1]) == "https://assets.blobbi.pet/items/arcade/arcade-ticket-v1.webp"
    and (.content | fromjson | .metadata.action) == null
    and (.content | fromjson | .metadata.itemId) == "cur_arcade_ticket"
  ' >/dev/null && echo PASS || echo FAIL
```

## 6. Activation procedure — only after §5 passes on BOTH relays

**Completed on 2026-07-28** — recorded here for the next definition. Do not start these until the event is confirmed present on both relays.

1. In `src/protocol/event-registry.ts`, change the Arcade Ticket's
   `status: 'reserved'` to `status: 'active'`.
2. `npm run docs:registry` to regenerate the registry document.
3. Add the ticket's published metadata to the exact-metadata table in
   `src/inventory/catalog.test.ts` (which covers `active` items), and update the
   reserved/active count assertions in `src/protocol/event-registry.test.ts`.
4. Confirm relay precedence in the app: the resolved definition's `source`
   becomes `"definition"` instead of `"fallback"`.
5. Confirm the artwork renders from the fetched definition, and that with relays
   unreachable the bundled fallback still renders the same artwork.
6. Full checks: `npx tsc -p tsconfig.app.json --noEmit`, `npx eslint`,
   `npx vitest run`, `npx vite build`.

Step 3 is what turns "we intend to publish this" into "this is published", and
the tests are written so that skipping it fails loudly.

### Known gap to decide during activation

`ItemBagModal` renders `definition.emoji` only — it has no `<img>` branch, so
the bag will show 🎟️ even once the artwork is live. This is pre-existing
behaviour shared by all 20 items (none other has artwork), not a regression.
`ArcadeTicketBalance` *does* follow the image → emoji resolution order. Decide at
activation whether to teach the bag the same order; it is a small change that
today would affect only this item.

### Two valid signings exist — this is fine

The publish command ran **twice**, 162 seconds apart, producing two
independently valid events for the same address:

| Event id | `created_at` | Seen on |
| --- | --- | --- |
| `9ba4cf0745fc827589fbfe3f981985c14f3ea4191ce25c0686ba0d4a152c63e6` | 1785217796 | ditto |
| `89901d7678d3bcab3043646e76cde0c47a7076e3f9ea17ab61baae2b407fe2b0` | 1785217634 | ditto, dreamith |

Their `tags` and `content` hash **identically** (`SHA-256(tags)` and
`SHA-256(content)` each collapse to one value across all three copies); only
`created_at`, and therefore `id` and `sig`, differ. kind:31632 is addressable, so
newest-wins per relay and both resolve to the same definition. No republish is
needed and no client can observe a difference.

### Why no event id is recorded in the canonical registry

The registry stores the **address**, not an event id, and deliberately so — this
publication is the demonstration. An event id is not a stable reference for an
addressable kind:

- it changes on every republish (artwork `-v2` will mint a new one);
- two valid ids already exist for this single definition, so "the published event
  id" is ambiguous on day one;
- which one a client resolves depends on which relay it reached.

Recording one in `src/protocol/event-registry.ts` would add a field that nothing
can validate, that goes stale silently, and that the generated document would
present as canonical — exactly the manually-drifting source the registry exists
to prevent. The address is the stable identity; the ids above are a
point-in-time verification record, which is what this section is.
